## 1. 지금 무엇이 있는가

### 1-1. "점검 세트"가 무엇인지부터

아이가 쓰는 학습앱(단원 하나에 HTML 파일 하나)에는 개념 탭이 서너 개, 퀴즈 탭 하나, 정리 탭 하나가 있다. 여기에 **⚡ 실전** 탭을 하나 더 붙인 것이 점검 세트다.

- **12문항 · 4지선다.** 아이가 답을 고르면 즉시 채점되고, 틀리면 **왜 그 답을 골랐는지**가 보기별로 뜬다.
- 틀린 원인마다 **"이 개념 다시 볼래?" 칩**이 뜨고, 그 칩을 누르면 같은 앱의 해당 개념 탭으로 바로 간다.
- 결과를 어디로 보내지 않는다. 점수도 등수도 없다. 앱 안에서 끝난다.

**파일 하나가 세트 하나**이고, 위치는 `exam_track/problem_bank/data/<세트>.js` 다. 파일 전체는 이 모양이다.

```js
// 점검 문제은행 — 통합과학1 Ⅲ. 지구 시스템
// 근거 학습앱: subject_hub/통합과학1/10_app/sci1_earth.html (탭: spheres 지권·수권 · cycle 물질순환 · plate 판구조론)
// ⭐ 취지: (이 세트가 무엇을 짚는지 두세 줄)
// ⭐ 앱 회피: (앱의 어떤 위젯·퀴즈와 겹치지 않게 했는지 — 실제로 확인한 것만)
// ⭐ 수식·기호는 유니코드로, 부등호는 &lt; &gt; 로 적는다 — innerHTML 삽입이라 KaTeX 가 돌지 않는다
window.BANK_SET = {                                  // ← 이 전역 이름이어야 엔진이 읽는다
  "id": "sci1_07",                                   // 파일명과 같게
  "subject": "통합과학",                              // 과목 대분류 (통합과학 / 통합사회 / 국어 / 수학 / 한국사)
  "unit": "과학:지구시스템",                          // ⚠️ topics.json 의 canonical 목록에 있는 것만 — §5-1
  "title": "Ⅲ. 지구 시스템 — 점검",                   // 앱의 단원 제목과 맞춘다
  "source_app": "subject_hub/통합과학1/10_app/sci1_earth.html",   // ⚠️ 없으면 이식 도구가 앱을 못 찾는다
  "created": "2026-09-08",
  "items": [ …12개… ]
};
```

`items` 의 원소 하나가 문항 하나다.

```jsonc
{
  "id": "sci1_07_003",             // <세트id>_<3자리 번호> — 위 래퍼의 id 가 sci1_07 이므로 이렇게 된다
  "type": "자료해석",              // 과목별 유형 — §3 참조. 화면에 칩으로 그대로 인쇄되므로 이름을 지어내지 않는다
  "level": "상",                   // 중상 / 상 / 최상
  "material": "표: 어떤 …",         // 제시문(선택). ⚠️ 이것이 있는 문항에만 C4 를 쓸 수 있다
  "stem": "이 자료에서 알 수 있는 것은?",
  "o": [
    { "t": "정답 보기" },                                    // 정답에는 cause·why 를 붙이지 않는다
    { "t": "오답 A", "cause": "C7", "why": "표의 둘째 줄만 보고 …" },
    { "t": "오답 B", "cause": "C3", "why": "지권과 수권을 뒤바꿔 … (지권 ↔ 수권)" },
    { "t": "오답 C", "cause": "C2", "why": "물질 순환의 방향을 모르고 …" }
  ],
  "a": 0,                          // 정답의 인덱스. 도구가 강제하지는 않지만 **0 으로 통일**하는 것이 관행이다
                                   // (엔진이 화면에서 보기를 섞으므로 위치 단서가 되지 않는다)
  "solve": {
    "key": "풀이 전 과정 + 마지막에 '확인:' 으로 시작하는 검산 한 줄",
    "trap": "이 문항에서 실제로 미끄러지는 지점과 그것을 막는 습관 한 줄"
  }
}
```

필수 필드는 `id` · `type` · `level` · `stem` · `o` · `a` · `solve` 이고, `material` 만 선택이다.
최상위에서는 `id` · `subject` · `unit` · `title` · `items` 가 필수, `source_app` 은 이식 도구가 쓰므로 사실상 필수, `created` 는 기록용이다.

이 시스템의 핵심은 `cause`(원인 코드)와 `why`(그 오답을 고르게 되는 사고 과정)다. **정답을 맞히는 것보다 왜 틀렸는지를 아이 자신이 읽는 것**이 목적이다.

### 1-2. 원인 코드 여덟 가지 (전문)

| 코드 | 이름 | 뜻 |
|---|---|---|
| **C1** | 문제해석 | 발문·조건을 놓치거나 잘못 읽음 |
| **C2** | 지식부재 | 해당 개념·사실을 아예 모름 |
| **C3** | 지식혼동 | 비슷한 둘 이상을 구별하지 못함 |
| **C4** | 적용실패 | 개념은 아는데 이 상황에 꺼내 쓰지 못함(전이 실패) |
| **C5** | 실행오류 | 방향은 맞았는데 처리 과정에서 틀림 |
| **C6** | 시간전략 | 실력이 아니라 배분·순서 문제 |
| **C7** | 자료해석 | 표·그래프·사료·지문에서 필요한 정보를 못 뽑음 |
| **C8** | 순서·연대 | 사건·절차의 시간 순서 감각 부재 |

문항에 쓰는 것은 **C1~C5 와 C7·C8** 이다. C6(시간전략)은 실제 시험 상황의 코드라 문항에는 쓰지 않는다.

작성 규칙 네 가지:

- **한 문항의 오답 셋은 서로 다른 코드**여야 한다. 같은 코드가 둘이면 진단이 뭉개진다.
- **C3 을 쓰면 `why` 에 혼동 쌍을 `(A ↔ B)` 로 반드시 적는다.** 실재하지 않는 쌍을 지어내면 안 된다.
- **C4 는 `material`(제시문)이 있는 문항에서만** 쓴다. "무엇을 꺼내야 하는지 몰랐다"는 진단은 꺼낼 대상이 화면에 있을 때만 성립한다.
- **산술이 실제로 맞으면 C5 가 아니다.** 계산은 맞는데 규칙을 모르는 것이면 C2 다.

### 1-3. 이미 끝난 과목

⭐ **두 가지를 구별해야 한다.** 헷갈리면 규격을 잘못 잡는다.

- **아이 오답 프로파일** = `causes.json` 에 적힌 것. *아이가 학교 시험에서 실제로 틀리는 이유*의 추정치다.
- **세트 실측** = 만들어진 문항의 오답에 실제로 붙은 코드 분포. **이쪽이 새 세트를 만들 때의 현실적 기준이다.**

| 과목 | 세트 | 문항 | 아이 오답 프로파일(캐논) | **세트 실측 — 오답 코드 분포** |
|---|---|---|---|---|
| 수학 (고1·고2 37단원) | 37 | 444 | C4 · C1 · C5 | (계산 과목이라 별개) |

| 통합사회2 | 5 | 60 | C4 · C3 · C7 | **C3 45 · C2 33 · C4 19 · C7 17 · C1 16 · C8 5** |

⚠️ **여기서 두 가지가 드러난다.**

1. **C2(지식부재)가 실제로는 최다 원인이다.** 캐논 프로파일에는 어느 과목에도 C2 가 없지만, 실제 세트에서는 통합과학2 125건 · 통합사회2 33건 · 한국사 54건으로 압도적이다. 개념형 오답을 만들면 자연히 C2 가 되기 때문이다. **새 세트에서도 C2 가 가장 많아지는 것이 정상이다.**
2. **통합과학2 에서 C5(실행오류)는 7건, 전체의 2 % 로 가장 드물다.** 캐논에는 지배 원인으로 적혀 있지만 실제로는 그렇지 않았다. 계산 문항 13개를 냈는데도 "진짜 계산 실수"로 진단할 오답이 별로 나오지 않았기 때문이다(대개는 공식을 모르는 C2 였다). **§8-④의 판단 근거가 이것이다.**

**난이도 실측:** 통합과학2 = 중상 21 · 상 63 · 최상 26, 통합사회2 = 중상 6 · 상 39 · 최상 15. 12문항 기준으로 대략 **중상 1~2 · 상 7~8 · 최상 2~3** 이다.

**유형 실측:** 통합과학2 = 개념구별 25 · 사례적용 20 · 자료해석 19 · 계산 13 · 복합개념 12 · 함정 9 · 탐구설계 9 · 순서배열 3. 통합사회2 = 사례적용 22 · 개념구별 9 · 복합개념 9 · 자료해석 8 · 관점비교 6 · 함정 5 · 순서배열 1.

## 2. 왜 수학 규격을 그대로 쓸 수 없는가

수학 세트는 **정답이 하나로 계산되는** 문항이다. 그래서 이런 것이 가능했다.

- 정답키를 **문항의 풀이와 다른 경로로 다시 계산**해 검산할 수 있었다(완전 열거·수치적분·시뮬레이션).
- 오답 셋의 값이 각각 **어떤 계산 실수에서 나오는지** 숫자로 확정할 수 있었다.
- 그래서 검증이 기계적으로 돌아갔고, 게이트가 잡는 것은 주로 `why` 문장의 층이었다.

세 과목은 정답이 **계산되지 않는다.** 통합과학1 은 계산 문항이 두어 개 있을 뿐이고, 통합사회1 은 개념 판단과 사례 적용, 공통국어2 는 지문 근거 대조다. 그래서 다시 계산해 확인할 수가 없다.

각 과목에서 **가장 큰 위험**도 다르다 — 통합과학1 은 **틀린 과학 사실을 쓰는 것**, 통합사회1 은 **가상 사례가 실제와 어긋나는 것**, 공통국어2 는 **지문에 없는 것을 정답 근거로 쓰는 것**이다.

**결론:** 검산 파일로 정답키를 재계산하는 단계를 그대로 쓸 수 없다. 대신 **다른 안전장치**를 세운다 — §4.

## 3. 과목별 규격 제안

### 3-1. 공통 규격 (세 과목 모두)

- **12문항 · 4지선다 · 정답은 `a: 0`**(화면에서 섞여 나오므로 위치 단서는 없다).
- **난이도** 중상 1~2 · 상 7~8 · 최상 2~3 (기존 세트 실측값. 수학은 중상 3~4 였지만 개념 과목은 상이 더 두껍다).
- **오답 셋은 서로 다른 원인 코드.**
- **`material`(제시문)이 있는 문항에서만 C4 를 쓴다.**
- **`solve.key` 는 풀이 + `확인:` 으로 시작하는 한 줄**, `solve.trap` 은 실점 지점과 습관 한 줄.
- 수식·기호는 **유니코드**로 적는다(², ³, √, ≤, ×, −). 부등호는 `&lt;` `&gt;` 로. **실전 탭은 KaTeX 를 다시 돌리지 않으므로 `$…$` 나 `\frac` 을 쓰면 글자가 그대로 보인다.**
- 앱 화면에 **시험·점수·등수·내신·합격**을 연상시키는 문구를 쓰지 않는다.
- 파일 머리말 주석에 **취지**와 **앱 회피 내역**을 적되, **실제로 확인한 것만** 적는다.

### 3-4. 공통국어2 — ⭐ 새 규격이 필요하다 (이 문서의 핵심)

지배 원인 **C7 · C1 · C3**. 국어는 문제은행이 처음이라 아래를 새로 정한다.

**국어가 다른 이유:** 정답의 근거가 **지문 안에** 있다. 개념을 알아도 지문을 잘못 읽으면 틀리고, 지문을 잘 읽으면 개념을 몰라도 맞힌다. 그래서 진단이 "무엇을 모르는가"가 아니라 **"어디를 잘못 읽었는가"**여야 한다.

**규격 제안:**

| 유형 | 비중 | 설명 |
|---|---|---|
| **근거찾기** | 3~4 | ⭐ 지문의 어느 문장이 이 판단의 근거인가. C7 의 자리 |
| **선택지대조** | 2~3 | 선택지의 말이 지문과 어긋나는 지점 찾기. C1·C7 |
| 표현·갈래 | 2 | 비유·운율·시점·서술 방식 같은 형식적 특징. C3 |
| 맥락추론 | 2 | 지문에 직접 없지만 근거로부터 따라 나오는 것. **지문 밖으로 나가면 안 된다** |
| 어휘·문맥 | 1~2 | 그 자리에서의 뜻. C2·C3 |

**국어에만 있는 규칙 세 가지:**

1. **`material` 은 지문 그 자체다.** 12문항 중 최소 8문항에 지문이 붙는다. 짧게 자르지 말고 판단에 필요한 만큼 준다.
2. **`solve.key` 의 첫 문장은 반드시 "근거 문장"이다.** `"근거: '…' 이 문장이 …임을 말한다."` 로 시작한다. 수학의 계산 검산 자리를 국어에서는 **근거 문장 지목**이 대신한다.
3. **`why` 는 "지문의 어디를 어떻게 잘못 읽었는가"로 쓴다.** "몰랐다"가 아니라 "이 문장을 이렇게 읽었다"로.

**⚠️ 국어에서 가장 조심할 것:** 문학 작품의 해석은 하나가 아니다. **해석의 여지가 있는 것을 정답으로 만들면 안 된다.** 정답은 지문에서 반박 불가능하게 따라 나오는 것이어야 하고, 애매하면 그 문항을 버린다.

**앱 상태 주의:** `kor2_chunhyang` 은 **이식 도구가 그냥 실패한다.** 자세한 것과 해법은 §5-2 에 적었다.

## 4. 검산을 대신할 안전장치

> ⚠️ **먼저 알아 둘 것 — 이 절은 신규 규칙이다.** `exam_track/problem_bank/verify/` 에는 지금 **수학 37개 파일만** 있다. 이미 라이브인 통합과학2 9세트 · 통합사회2 5세트 · 한국사 8세트 **22세트는 검산 파일 없이** 나갔다. 아래는 "그때보다 한 겹 더 두자"는 제안이고, 실제로 하면 15세트 × 12문항 = **180줄의 문장을 새로 써야 한다.** 할지 말지는 §8-⑤ 에서 정한다.

수학에서는 `verify/<세트>.js` 라는 검산 파일이 정답키를 독립적으로 재계산했다. 세 과목에서는 그것이 불가능하거나 일부만 가능하다. 대신 이렇게 한다.

### 4-1. 통합과학1 — 계산 문항만 검산 파일을 쓴다

12문항 중 계산이 2개라면 그 2개만 `verify/sci1_NN.js` 에 넣는다. 나머지는 아래 4-3 으로.

```js
module.exports = function ({ chk }) {
  // ⚠️ verify_set.js 는 12문항 **전부**에 chk 를 요구한다. 하나라도 빠뜨리면 "미검산"으로 세어 실패한다.
  //    그래서 계산 문항은 코드로, 개념 문항은 "근거가 앱의 어디에 있는지"를 문자열로 남긴다.

  // 계산 문항 — 문항의 풀이와 다른 경로로 다시 구한다
  chk(4, '2.24 L', '몰수 0.1 × 22.4 = ' + (0.1 * 22.4) + ' L · 거꾸로 2.24/22.4 = ' + (2.24 / 22.4) + ' 몰');

  // 개념 문항 — 자동 검증이 아니라 **추적 가능성**을 위한 기록이다
  chk(1, '정답 보기 문구', '앱 sci1_earth 의 spheres 탭 ✅박스에 이 정의가 그대로 있다 — 사람이 대조함');
};
```

`chk(문항번호, 정답보기문구, 근거)` 에서 **둘째 인자가 데이터의 정답 보기 `o[0].t` 와 글자 그대로 일치해야** 통과한다. 그래서 개념 문항이라도 최소한 "정답 보기를 다시 한 번 옮겨 적는" 일은 하게 된다.

즉 **계산은 코드로, 개념은 "앱의 어디에 근거가 있는지"를 문자열로** 남긴다. 후자는 자동 검증이 아니라 **추적 가능성**을 위한 것이다.

### 4-2. 통합사회1·공통국어2 — 근거 위치를 명시한다

계산이 없으므로 전 문항에 대해 이렇게만 적는다.

```js
chk(3, '정답 보기 문구', '앱 soc1_nature 의 view 탭 "생태중심주의" 박스 3번째 문단이 근거 · 다른 세 보기는 그 문단과 어긋남');
chk(7, '정답 보기 문구', '지문 2문단 "…" 이 근거 · 보기 B 는 3문단을 4문단으로 오독해야 나옴');
```

### 4-3. 세 과목 공통 — 검증 게이트를 두 번 돌린다

수학은 게이트를 한 번 돌렸다. 세 과목은 **성격이 다른 게이트를 두 번** 돌린다.

**게이트 A — 사실 검증** (Opus, 세트 1개당 1에이전트)
- 정답이 정말 정답인가. **과학적 사실·사회 개념·문학 해석이 틀리지 않았는가.**
- 복수 정답이 없는가. 해석의 여지로 다른 보기도 참이 되지 않는가.
- 오답의 `why` 를 따라가면 그 보기에 닿는가.
- 원인 코드가 정의대로 붙었는가. C3 의 혼동 쌍이 실재하는가.

**게이트 B — 앱 대조** (Opus, 세트 2개당 1에이전트)
- 정답의 근거가 **근거 앱 본문에 실제로 있는가.** 없으면 문항을 깎지 말고 **앱에 박스를 채운다.**
- 앱의 **퀴즈 배열·예제·개념 박스**와 문항이 겹치는가.
- 앱의 **인터랙티브 위젯이 정답을 화면에 인쇄하는가.** ⭐ 이것이 수학 배치에서 가장 많이 잡힌 결함이다(다섯 회차 연속 11건). 슬라이더의 `min`/`max`/`step` 을 읽어 **도달 가능한 값을 전부** 만들어 보게 한다. **그 앱이 링크로 여는 다른 앱까지 본다.**
- 화면 안전 — LaTeX 잔재, `<` 뒤에 한글이 붙어 태그로 먹히는 자리, 부등호 엔티티.

**부르는 법.** 서브에이전트에게 **파일 수정 권한을 주지 않고 보고만** 시킨다.

```
Agent(subagent_type: "general-purpose", model: "opus", prompt: …)
```

프롬프트에 반드시 넣을 것:

1. **검증 대상 파일 경로**와 **함께 읽어야 할 근거 앱 경로**(탭 id 목록까지).
2. **데이터 형식 설명** — §1-1 의 스키마를 그대로 붙여 넣는다. 에이전트에게는 이전 대화가 없다.
3. **원인 코드 정의** — §1-2 의 표를 그대로 붙여 넣는다.
4. **점검 항목** — 위 게이트 A/B 의 목록.
5. **"파일을 절대 수정하지 마십시오. 보고만 하면 됩니다."**
6. **보고 형식** — 아래 넷으로 고정한다.
   - **치명** — 반드시 고쳐야 하는 것. 각 건에 문항 id · 무엇이 왜 틀렸는지 · **구체적인 고침안**(바꿀 수치나 문구를 직접 제시)
   - **보통** — 고치는 편이 나은 것
   - **경미** — 판단에 맡기는 것
   - **확인한 것** — 통과한 항목을 한 줄씩
7. **"고침안을 낼 때는 그 수치가 실제로 성립하는지 직접 확인한 뒤 제시해 주십시오."**

⚠️ **게이트 보고를 그대로 받아쓰지 않는다.** 근거가 약한 지적은 반려하고 이유를 `REVIEW.md` 에 남긴다. 반대로 게이트가 준 고침안을 반영할 때는 **그 수치를 다시 검산**한다 — 수학 배치에서 게이트의 제안 수치가 다른 오답과 충돌한 적이 있다.

## 6. 이미 겪은 실패 — 반복하지 말 것

수학·과학·사회·한국사 배치에서 검증 게이트를 서른여섯 차례 돌리며 잡은 것 중, **세 과목에도 그대로 적용되는 것**만 추렸다. 회차별 상세는 `REVIEW.md` 에 있다.

1. **오답은 값이 아니라 경로가 닿아야 한다.** `why` 에 적은 실수를 그대로 따라갔을 때 **그 보기**에 닿아야 한다. 다른 보기나 정답에 착지하면 그 오답은 죽은 것이다. 12회 연속 여기서 치명이 나왔다.
2. **앱 위젯을 파라미터 전 조합으로 훑는다.** 헤더에 "피했다"고 적는 것과 실제로 피한 것은 다르다 — 적어 놓고도 정작 정답이 범위 한복판이었던 적이 세 번이다. **그 앱이 링크로 여는 다른 앱까지** 본다.
3. **근거 박스를 채울 때 문항과 같은 수를 쓰지 않는다.** "앱에 근거 없음" 지적을 받고 박스를 넣었더니 그 박스가 문항을 통째로 미리 풀어 놓은 적이 있다. 규칙은 적되 예시는 다른 값으로.
4. **한 문항 안에 같은 원인 코드가 둘이면 안 된다.** 게이트 지적을 따라 코드를 옮기다 이 위반이 다섯 번 생겼다. `check_bank.py` 가 보지 않으므로 직접 센다.
5. **앱 화면에 시험·점수·합격을 쓰지 않는다.** 한 문항이 "어떤 시험에서 합격할 확률"로 시작해 잡혔다. 상황을 바꾸면 내용을 그대로 두고 고칠 수 있다.
6. **단원 번호를 학습앱과 맞춘다.** 세트 제목의 단원 번호가 앱과 어긋난 일이 네 번 재발했다. 앱의 제목을 그대로 옮겨 적는다.
7. **정답만 유독 길거나 형식이 다르면 안 된다.** 보기 넷의 길이·형식을 나란히 맞춘다. 한 세트에서 정답이 전부 최장 보기였던 적이 있다.
8. **"구할 수 없다 / ~ 없다" 가 정답인 문항을 세트마다 하나쯤 둔다.** 그런 보기가 늘 오답이면 아이가 형태만으로 지운다.

⚠️ **도구 하나가 오탐을 낼 자리가 있다.** `drill_render_check.js` 는 렌더 결과에 `C1`~`C8` 이 보이면 "원인 코드가 화면에 노출됐다"며 실패시킨다. 그런데 **통합과학1 생명 시스템 단원에서 `C3 식물`·`C4 식물` 같은 정상 표기**를 쓰면 그것도 걸린다. 그 단원을 쓸 때는 표기를 `C₃ 식물`(아래첨자)로 하거나, 걸리면 도구의 그 검사만 예외 처리한다.

### 통합사회1 을 하며 확정된 것 (남은 두 과목에도 그대로 쓴다)

- **검산 파일을 도입했다(§8-⑤ 의 (가) 안).** 계산이 없어 다시 계산할 것이 없으므로, 검산이 **앱 HTML 을 읽어 정답 근거 구절을 찾게** 짰다. 공용 헬퍼 `exam_track/problem_bank/verify/_lib_concept.js` 에 `appSource(과목폴더, 앱파일)` 와 `structCheck(S, {set})` 두 개가 있고, 세트별 검산 파일은 이렇게 시작한다.
  ```js
  const { appSource, structCheck } = require('./_lib_concept');
  const src = appSource('통합사회1', 'soc1_perspective.html');
  module.exports = function ({ S, chk }) {
    chk(1, '정답 보기 문구', 'lens 탭 · ' + src('앱에 있어야 할 근거 구절'));
    …
    structCheck(S, { set: 'soc1_01' });
  };
  ```
  `structCheck` 는 `check_bank.py` 가 보지 않는 층을 본다 — 오답 코드 중복 · C3 혼동쌍 표기 · C4·C7 의 material 전제 · C5/C8 오용 · 금지 문구 · `확인:` 줄 · **보기 길이의 형태 단서**. 계산이 있는 과목(통합과학1 일부)은 `structCheck(S, { set, allowC5: true })` 로 켠다.
- **말투 휴리스틱을 막는다.** 정답이 늘 온건하고 오답이 늘 극단이면 개념 없이 찍힌다. 세트마다 온건한 오답을 몇 개 심고 단정형 정답을 한둘 둔다.
- **퀴즈는 문항뿐 아니라 `e:` 해설까지 대조한다.** 해설이 오답을 미리 지워 주는 사례가 나왔다.
- **가상국 이름은 갑국·을국·병국·정국 순으로.**

**드는 시간(수학 배치 실측 기준):** 세트 하나에 출제 + 검산 + 게이트 2회 + 반영 = **반나절**이다. 15세트면 **대략 7~8일치 작업**이고, 한 세션에 2~3세트씩 하면 여섯 세션쯤 걸린다.

세 과목을 따로 보면 — 통합과학1 8세트(≈4일) · 통합사회1 4세트(≈2일) · 공통국어2 3세트(≈1.5일). **국어가 가장 짧지만 규격이 처음이라 첫 세트에서 시간이 더 든다.**

- 도입하면 15세트 × 12문항 = **180줄의 근거 문장**을 더 쓴다. 계산이 없는 과목에서는 자동 검증이 아니라 "근거가 앱의 어디에 있는지"를 남기는 기록에 가깝다.
- **(가) 도입한다** — 근거 위치가 파일로 남아 나중에 앱을 고칠 때 추적된다. 대신 세트당 한두 시간이 더 든다.
- **(나) 기존 22세트처럼 생략한다** — 게이트 두 겹으로 충분하다고 보는 쪽.
- 제안은 **(가)** 다. 앱과 문항의 연결이 끊어지는 것이 이 시스템에서 가장 조용히 위험한 일이기 때문이다.
