## 라운드 1 — Claude 답변 (원문 전문)

좋은 타이밍입니다. 문제 형태(별도앱·문항수·엔진)는 전부 아래에서 파생되는 하위 결정이라, 그걸 미루고 근본을 잡는 게 맞습니다. 엔지니어 언어로 말하면 — 지금까지 저는 **스펙 없이 구현**을 자율로 돌린 셈이고, 이제 **스펙(목적함수 + 대상 모델 + 제약)**을 같이 확정하자는 것으로 이해했습니다.

먼저 제가 실제로 어떤 렌즈로 만들었는지 정직하게 복기(+비판)하고, 그 위에서 문제 만들기의 관점을 제안하고, 마지막에 4과목 공통 재점검 프레임을 던지겠습니다.

### 1. 지금까지 앱을 만든 실제 렌즈 (+ 정직한 비판)

실제 기준은 `CONTENT_PRINCIPLES.md`의 **8원칙**이었습니다: 깊이 / 훅(흥미) / 단계 / 평생기억 / 인사이트 / 실생활 / 산업·진로 / 정확성.

이게 최적화한 것은 **"교과서보다 재미있고 깊고 정확한 읽을거리 + 확인 퀴즈"** — 결과물은 *잘 만든 인터랙티브 교재*에 가깝습니다.

정직한 한계 셋:
- **(a)** 8원칙은 **콘텐츠 품질 체크리스트**지, "이 아이가 실제로 배우고 남기는가"에 대한 **학습 이론**이 아닙니다. 좋은 재료 목록이지 조리 설계가 아님.
- **(b)** 자율진행에 유리한 지표(커버리지·완성도·정확성)를 은연중 최적화 → **passive(읽기) 편중**. 아이가 하는 행위는 대부분 "읽기", 가끔 "퀴즈". 학습과학이 말하는 강한 학습(직접 인출·생성·예측)의 비중이 작습니다.
- **(c)** 대상이 "일반 고1"이었지 **당신 아이**가 아니었습니다. 현재 수준·동기·어디서 튕겨나가는지를 모른 채 만들었습니다.

### 2. 근본 질문: 목적함수를 먼저 정하자

모든 하위 설계(콘텐츠 톤·문제 유형·피드백·반복)는 **"무엇을 위해?"**에서 파생됩니다. 목표는 스펙트럼이고 서로 **충돌**합니다:

> 내신 성적 ── 수능 기초 ── 진짜 이해·사고력 ── 평생 교양·지적 흥미 ── 메타인지(공부하는 법)·자기주도

핵심 충돌: **내신 최적화**(교과서 프레임 그대로 암기)와 **이해·흥미**는 자주 반대 방향입니다. 지금 제 앱은 오른쪽(이해·교양)에 서 있는데 — 아이의 당면 통증이 **내신 시험**이라면 "아름답지만 지금 성적엔 안 꽂히는" 물건일 수 있고, 반대로 내신만 쫓으면 외우고 잊는 아이를 만듭니다. 당신이 원하는 건 그 극단이 아닐 겁니다.

→ **1순위 목적함수가 무엇인가**가 이 논의의 첫 매듭입니다.

### 3. 왜 하필 "앱"인가 (자작 앱의 유일한 우위)

이걸 못 박아야 방향이 섭니다. 아이에겐 이미 교과서·인강·문제집이 있고, 그것들은 프로가 만든 겁니다. 앱이 *예쁜 교과서*면 **중복이자 열등재**입니다. 자작 앱이 그들이 못 하는 것:
- **능동성** — 읽는 게 아니라 *조작·예측·결정*하게 만든다(수요·공급 곡선을 밀어보기, 연표를 배열해보기).
- **즉각·풍부한 피드백 루프** — 틀리면 *왜 틀렸는지 + 개념으로 되돌리기 + 나중에 다시*.
- **타이트한 맞춤** — 딱 이 아이의 약점·흥미·진로에 맞춤.

지금 제 앱은 이 세 가지의 잠재력을 절반만 쓰고 있습니다(퀴즈=능동의 일부일 뿐).

### 4. 문제(problem)의 관점: 평가용 vs 학습용

당신이 물은 "문제는 어떤 목적으로?"의 핵심입니다. 문제는 완전히 다른 두 물건이 될 수 있습니다:
- **평가용(assessment):** 아는지 *측정*. 실전 조건·점수·등수 → 내신/모의 시뮬.
- **학습용(learning):** 문제로 *가르침*. 인출연습 + 풍부한 피드백 + 의도된 난이도 + **흔한 오개념을 일부러 밟게 하고 교정**.

제 PLAN의 `solve{근거·오답분석·함정·링크}`는 이미 학습용 본능입니다. **제 입장: 학습용 우선.** 이유 — 문제의 학습 가치는 문제 자체가 아니라 **피드백 + 재도전**에 있고, 그게 정확히 자작 앱의 우위입니다. 평가용은 기출·문제집이 이미 잘하니 우리가 열등하게 재현할 이유가 적습니다. (내신 대비는 "학습용으로 개념을 굳힌 뒤 → 실전 기출로 마감"이 순서.)

### 5. 4과목 공통 재점검 프레임

엔지니어 프레임: 학습 = **아이의 현재 상태(state) → 목표(target)**로 가장 효율적으로 옮기는 시스템. 우리가 설계할 "아키텍처" = 콘텐츠 + 문제 + 피드백 루프 + 반복 스케줄. 제약 = 아이의 시간·동기·내신 시계.

이 시스템을 설계할 때 쓸 학습과학 앵커(짧게):
- **인출연습(retrieval):** 읽기보다 "떠올려 답하기"가 기억을 만든다.
- **간격 반복(spacing):** 같은 걸 시간 두고 다시.
- **교차(interleaving):** 유형 섞기 > 한 유형 몰아치기.
- **생성효과(generation):** 정답을 *보기 전에 스스로 만들어보게* 하면 남는다.
- **예제→점진 페이딩:** 처음엔 완전풀이, 점점 스스로.
- **전이(transfer):** 새 사례에 적용될 때만 "이해"다.

→ 8원칙(콘텐츠 재료)을 폐기하는 게 아니라, 그 위에 **이 학습 루프(설계 원리)**를 얹어 4과목 전부를 다시 보는 겁니다.

### 6. 내가 지금 모르는 것 = 논의 입력값

정직히, 이걸 모르면 좋은 스펙을 못 씁니다:
- **어느 아이인가.** 진로·성향(축구분석가 트랙과 연결되나?).
- **각 과목과의 관계:** 좋아함/싫어함, 잘함/뒤처짐, 긴 글을 읽나 튕기나.
- **당면 통증:** 다음 시험이 급한가, 장기 사고력이 본질인가.
- **사용 방식:** 아이 혼자 쓰나 / 당신과 함께 보나 / 아이가 *직접 만드는 데 참여*하나(부자 공동 프로젝트도 강력한 학습).

---

**제 추천 출발선(반박 환영):** 목적함수 = *이해·사고력 위주(70%) + 내신 방어(30%)*, 콘텐츠는 읽기 비중을 줄여 "예측→답→피드백" 능동 루프로 재설계, 문제는 학습용 우선. **단, 아이 상태를 듣고 조정.**

논의는 순서가 중요합니다. **2번(목적함수)과 6번(아이가 누구이고 지금 어떤 상태인가)**을 먼저 못 박으면 3·4·5는 공중에 뜹니다. 그래서 제안 — **이 아이가 누구이고, 각 과목을 어떻게 느끼고, 당면 통증이 무엇인지부터** 들려주세요. 거기서부터 목적함수를 같이 고정하고, 그 다음 콘텐츠·문제 설계로 내려가겠습니다.

### A. 두 갈래 분리 — 동의. 그리고 이미 디스크에 존재한다.

분리가 옳은 이유는 취향이 아니라 **시스템 파라미터가 전부 다르기 때문**입니다.

| 축 | 내신 갈래 (Exam) | 흥미 갈래 (Curiosity) |
|---|---|---|
| 목적함수 | 실점 최소화 — 아는데 틀리는 것 제거 | 아이가 스스로 더 알고 싶어지게 |
| 시간 지평 | 시험일까지 (주 단위 데드라인) | 수년 (마감 없음) |
| 리듬 | 시험 캘린더 스프린트(중간·기말·수행) | 상시 백그라운드, 아이 주도 |
| 콘텐츠 권위 | **학교 교과서·프린트·기출이 정본** | 세상 전체가 소재 |
| 성공 지표 | 오답 재발률 ↓, 점수 | **아이가 시키지 않아도 다시 여는가**, 아이 질문의 질 |
| 실패 모드 | 범위 누락, 같은 실수 반복 | 지루함 → 안 씀 |
| 주도권 | 부모/시스템이 끌고 감 | 아이가 끌고 감 |

**중요:** 이미 저장소가 그렇게 나뉘어 있습니다 — `26_High_1-1/`(과목별 `-중간`, `02_text`, `10_오답노트`, 수행평가) + 빈 `2607_High1_Final/` = **내신 갈래**. `subject_hub/`(16단원앱+허브) = **흥미 갈래**. NCC 2개는 새 구조를 만드는 게 아니라 **이미 있는 두 덩어리를 승격**시키는 일입니다.

**단, 완전 분리는 낭비 — 연결 고리 하나만 남깁니다(느슨한 결합·단방향):**
`오답의 약점 태그(예: 수학:이차함수)` → `흥미앱의 해당 개념 페이지`. 내신에서 발견된 구멍을 흥미쪽에서 메우는 링크. 반대 방향(흥미→내신)은 만들지 않습니다. 흥미 갈래에 시험 냄새가 스미면 그 순간 죽습니다.

**직접적 결론 하나:** 지금 대기 중인 **"사회과 고난도 문제"는 내신 갈래 소속**입니다. `subject_hub`(흥미)에 붙이려던 계획을 취소하고 내신 NCC로 이관합니다. 흥미앱 안의 퀴즈는 "이해 확인"용으로만 남깁니다.

### B. 내신 갈래 — 오답노트가 심장. 지금의 진짜 갭.

이미 있는 자산(수학 한정으로는 거의 완성형):
`se-math-error-note`(7섹션 노트+단계별 앱) · `se-math-figure`(SVG/JSXGraph) · `se-math-practice`(쉬운/비슷한/응용 3×3) · `se-agent-math-error-workflow`(오케스트레이션) · `se-figcrop`(시험지 캡쳐→그림) · `se-agent-app-reviewer`(검증 게이트).

**갭 1 — 과목 일반화가 단순 복제가 아니다.** 오답의 *성질*이 과목마다 다릅니다.
- 수학: 절차·계산·조건 누락 → "다시 풀면 맞나"로 검증 가능
- 과학: 개념 오해 + 계산 + 자료해석 혼재
- 사회·한국사: **개념 혼동·용어 혼동·자료해석 실패·함정(부정형)·연대 감각** → 다시 풀기보다 *구별 훈련*이 약
- 국어: 근거 문장 찾기 실패 (지문 의존 → 오답노트 형태 자체가 다름)
- 영어: 어휘/구문/추론

→ 과목별 **오답 유형 분류체계(taxonomy)**를 먼저 정의해야 합니다. 이게 없으면 결과물이 "해설지 재생산"이 되고, 학원 해설지보다 나을 이유가 없어집니다. **오답노트의 가치는 해설이 아니라 "내가 왜 틀렸는지의 패턴화"에 있습니다.**

**갭 2 — 누적·재출제 루프가 없다 (가장 큰 구멍).** 현재는 문항 단위 산출물을 만들고 끝. 약점 태그는 문서 안에만 있고 **누적되지 않고, 다시 물어보지 않습니다.** 학습과학이 가장 확실하게 말하는 두 가지(인출·간격반복)를 지금 시스템은 안 쓰고 있습니다.
→ 필요한 것: **약점 태그 DB(과목·단원·유형·발생일·재시도 이력) + 재출제 스케줄러**. 이게 내신 갈래의 핵심 미싱 피스이며, 오답노트 스킬 확장보다 우선순위가 높다고 봅니다.

**갭 3 — 입력 파이프라인.** 시험지 캡쳐 → 텍스트화가 수작업·OCR 의존. 아이가 직접 "이거 틀렸어"를 넣는 경로가 없습니다. 아이를 루프에 넣으려면 입력이 30초 안에 끝나야 합니다.

**내신 NCC의 3대 컴포넌트:** ① 입력(시험지/문제 → 구조화) → ② 오답 처리(노트+앱+연습, 과목별 taxonomy) → ③ **누적 약점 DB + 재출제**(신규, 최우선). 고난도 문제은행은 ③의 재료로 들어갑니다.

### C. 흥미 갈래 — "진짜 AI 앱" 가능한가? (기술적으로 가능. 단, 이유를 먼저 정해야.)

먼저 아키텍처. 현재 앱은 **GitHub Pages 정적 HTML = 서버 없음 = 비밀키 둘 곳 없음** → Claude API 직접 호출 불가(키가 소스에 노출).

| 옵션 | 방식 | 장점 | 단점 |
|---|---|---|---|
| ① BYO-key | 브라우저 localStorage에 API 키 저장 | 정적 유지, 즉시 가능 | **키 평문 노출·비용 무방비** — 권장 안 함 |
| ② 서버리스 프록시 | Vercel Function이 키 보관, 앱은 호출만 | 키 안전, **일일 예산·레이트리밋·시스템프롬프트를 서버에서 강제**, 대화 로그 수집 가능 | 인프라 1개 추가(배포·모니터링), 무료 티어 관리 |
| ③ Claude Code 자체 | 아이가 CLI/데스크탑에서 대화 | 가장 강력(파일·도구·기억) | 폰 불가, 아이 진입장벽 |
| ④ claude.ai Artifact | claude.ai 내부에서 실행 + 런타임 모델 호출 | 키·배포 걱정 없음 | 아이 계정 필요, 우리 Pages 생태계와 분리 |
| ⑤ **하이브리드(추천)** | 앱 90%는 기존 정적, **"질문하기/설명해보기" 버튼만** ②로 | 빠르고 공짜인 부분은 그대로, AI는 꼭 필요한 곳에만 | — |

**더 중요한 질문: AI를 붙이면 뭐가 좋아지나?** 그냥 챗봇이면 아이가 이미 ChatGPT/Claude로 할 수 있고, 우리 앱은 열등한 복제품이 됩니다. 자작 AI앱의 유일한 우위는 **컨텍스트 + 역할 고정**입니다:
- 아이가 **지금 보고 있는 단원·문항을 아는 상태**로 대화 (컨텍스트 주입)
- **답을 바로 주지 않는 튜터**로 시스템 프롬프트를 서버에서 고정 (소크라테스식 힌트 사다리)
- 아이의 **약점 태그·오답 이력**을 알고 있음 (내신 갈래와의 단방향 링크가 여기서 값을 함)
- 대화 로그가 남아 **부모가 무엇을 어려워하는지 볼 수 있음** — 조용한 대박 기능
- 우리 앱의 **검증된 콘텐츠를 컨텍스트로 주고 "이 자료 범위에서만" 제약** → 환각 억제 (미니 RAG)

**킬러 기능 후보 3개 (정적 앱으로는 절대 불가능한 것들):**
1. **🗣️ 설명해보기(파인만) 모드** — 아이가 개념을 자기 말로 설명 → AI가 빠진 부분·틀린 부분을 짚고 되물음. *생성효과 + 인출연습의 정석.* 제 1순위 추천.
2. **🪜 힌트 사다리** — "모르겠어" 누르면 답 대신 한 칸짜리 힌트, 계속 눌러야 답. 스스로 도달할 확률을 최대화.
3. **♾️ 무한 변형문제** — 틀린 문항의 변형을 즉석 생성 + 채점. (`se-math-practice`의 실시간판)

**리스크와 가드레일:** 답 뽑아쓰기(치팅) → 답을 안 주는 프롬프트 + 힌트 단계 로깅 / 환각(특히 역사·사회 팩트) → 컨텍스트 제약 + "확실하지 않으면 모른다고 말하기" / 비용 → 서버 측 일일 캡 / 프라이버시 → 아이 대화가 어디에 남는지 명시.

## 라운드 3 — Claude 응답

### A. BYO-key란 무엇이고 왜 탈락인가

**BYO = Bring Your Own Key.** 앱에 API 키 입력란 → 브라우저 `localStorage` 저장 → 브라우저가 직접 `api.anthropic.com` 호출. 서버가 없어 현재 정적 배포를 그대로 두고 AI를 붙일 수 있다. Anthropic API는 이를 허용하되 헤더를 강제한다:

```
anthropic-dangerous-direct-browser-access: true
```

**헤더 이름 자체가 결론.** 탈락 사유 셋:
1. 키가 아이 폰 브라우저에 평문 → 유출 시 **당신 계정에 무제한 과금**.
2. **강제가 클라이언트에 있음** — "답을 안 주는 튜터" 규칙을 브라우저 JS에 두면 개발자도구로 우회 가능. (RTL 비유: 어서션을 DUT 안에 넣는 꼴. 검증 로직은 DUT 밖에 있어야 한다.)
3. 로그 수집 불가 → 부모 리뷰 기능 원천 불가.

→ **② Vercel 서버리스 프록시로 확정.**

### B. 확정 아키텍처

```
[GitHub Pages 정적 앱] --fetch--> [Vercel Function /api/tutor] --> [Anthropic API]
 (기존 그대로, 90%)                 ├ ANTHROPIC_API_KEY (서버 env)
                                   ├ 시스템프롬프트 서버 고정(아이가 못 바꿈)
                                   ├ 단원 콘텐츠 컨텍스트 주입(검증된 범위 내 답변 → 환각 억제)
                                   ├ 일일 예산 캡 + 레이트리밋
                                   ├ 가족 패스코드(공개 URL 무단호출 차단)
                                   └ 대화 로그 → 부모 리뷰
```

### C. 비용 (2026-07 기준 실단가, 환율 1,400원)

1회 주고받기 = 시스템+단원콘텐츠 3,000tok(캐시) + 질문 500 + 응답 400 가정. 프롬프트 캐싱 시 반복 콘텐츠는 1/10 단가.

| 모델 | 입력/출력 per MTok | 1회 | 월 500회(하루 ~17회) |
|---|---|---|---|
| Opus 5 | $5 / $25 | 약 20원 | 약 9,800원 |
| Sonnet 5 | $3 / $15 (8/31까지 $2/$10) | 약 12원 | 약 5,900원 |
| Haiku 4.5 | $1 / $5 | 약 4원 | 약 2,000원 |

**비용은 제약이 아니다.** 서버 일일 캡 $1이면 사고가 나도 월 4만원 상한. 권장=Opus 5(팩트 정확성·설명채점), 비용 최적화 시 Sonnet 5도 충분. **모델 선택은 Nick 결정.**

### D. 아이 = 사용자(비제작자)의 설계 함의

제약이 아니라 명확한 스펙.
- **마찰 제로**: 링크 하나, 로그인·설치 없음, 폰 3초. 패스코드는 기기별 1회 저장.
